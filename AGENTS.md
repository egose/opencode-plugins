# AI contributor guide

## Repository purpose and layout

This repository is a collection of independent OpenCode V2 plugins, not one
aggregate plugin. Read the root README and the affected package's README before
making changes.

- `packages/<plugin-name>/`: one independently installable npm workspace per plugin.
- `packages/<plugin-name>/src/index.ts`: default `Plugin.define` server entrypoint.
- `packages/<plugin-name>/test/`: package tests and synthetic fixtures.
- `examples/`: user-facing OpenCode configuration examples; these are not active
  repository or user configuration.
- `package.json`, `package-lock.json`, `tsconfig.base.json`, `.prettierrc.json`:
  shared workspace configuration and development tools.
- `.github/`: npm-based CI — `test.yml` runs `npm run check` as the quality
  gate, `pre-commit.yml` runs the pre-commit hooks, `release-tag-changelog.yml`
  (manual dispatch) creates release-candidate PRs and `v*.*.*` tags, and
  `release.yml` publishes GitHub releases on those tags; composite actions live
  under `.github/actions/`.
- `.pre-commit-config.yaml`, `.bin/commitlint.sh`, `commitlint.config.mjs`,
  `requirements.txt`: optional local Git hook linting (prettier, commitlint)
  driven by Python's pre-commit framework.
- `VERSION`, `.release-it.json`, root `package.json` `version`: release
  versioning. `npm run release` (release-it) bumps `VERSION`, regenerates
  `CHANGELOG.md` via `npm run changelog` (`@repo-toolkit/changelog`), and tags
  `v<version>`. npm publishing stays disabled; plugins are consumed from tags.
- `scripts/validate-release-tag.sh`: release-tag validation used by
  `release.yml`. `CHANGELOG.md` is generated by the release flow — do not
  hand-edit it.
- `renovate.json`, `.tool-versions`: dependency automation and local asdf tool
  pins (Node and Python only; this repo does not use Bun, Helm, or Docker).

## Implementation conventions

- Target OpenCode V2. Check the current official documentation before changing
  plugin APIs, hooks, loading instructions, or configuration syntax:
  - <https://opencode.ai/docs/build/plugins>
  - <https://opencode.ai/docs/build/plugins/server>
  - <https://opencode.ai/docs/plugins>
  - <https://opencode.ai/docs/config>
- Keep each plugin independently installable. The root package stays private and
  must not export an entrypoint that enables all plugins.
- This is an npm/Node repository: `package-lock.json` is the only lockfile, CI
  installs with `npm ci`, and there are no Bun scripts or Bun configuration. Do
  not reintroduce `bun.lock`, `bun`-prefixed commands, or Bun-specific tsconfig
  options; plugins run inside OpenCode regardless of development toolchain.
- Commits follow Conventional Commits, enforced by commitlint
  (`commitlint.config.mjs`): types are build, chore, ci, docs, feat, fix, perf,
  refactor, revert, style, test, e2e; scopes are 2-35 characters.
- Declare runtime dependencies in the affected package; share development tools
  at the root. Update the npm lockfile when dependencies or workspaces change.
- Follow the existing TypeScript ESM style, explicit `.ts` relative imports,
  strict type checking, and Prettier configuration. Existing server packages
  export TypeScript directly and do not require a build step.
- Keep package names and `Plugin.define` IDs unique and stable. Ensure `exports`
  and `files` include everything needed when installed outside the workspace.
- New plugins need a README, `typecheck` and `test` scripts, a package tsconfig
  extending `../../tsconfig.base.json`, and an entry in the root plugin table.
- Document external executable prerequisites and configuration options. Do not
  silently install or download external programs.

## Secret-guardrail invariants

- Gitleaks is a user-installed CLI dependency, never a bundled binary or npm
  installation side effect. Resolve it portably; do not hard-code user paths.
- Preserve the documented best-effort, fail-open behavior unless the user
  explicitly requests a behavior change. Do not claim guaranteed secret blocking.
- Prompt redaction changes canonical `prompt.text` before persistence; context
  redaction changes only the outgoing draft, not stored history. Preserve
  attachments and clear stale mention metadata when prompt text changes.
- Dispatch protection currently uses `context` only. Do not describe it as
  protecting separate title, compaction, or transient generation requests.
- Keep scan input, reports, and cached secret values in memory. Logs and warnings
  must contain metadata only, never raw text, secrets, reports, scanner stderr,
  or exception messages that might contain sensitive data.
- Preserve batching, deduplication, TTL/LRU caching, and longest-first exact
  replacement. Apply event-local findings even if the LRU evicts them, and apply
  cached findings when a fresh scan fails. Never cache scanner failures.
- Use synthetic fixtures, not real credentials. Tests must work without Gitleaks
  installed or an OpenCode server running.

## Verification

Use Node.js 22 or newer and npm. From the repository root:

```sh
npm ci
npm run check
```

For focused work:

```sh
npm test --workspace opencode-secret-guardrail
npm run typecheck --workspace opencode-secret-guardrail
npm pack --workspace opencode-secret-guardrail --dry-run
```

Substitute the affected package name for other plugins. Run `npm run format`
when needed. For runtime or packaging changes, also verify an installed package,
not only a workspace-linked import. Add regression tests for changed behavior
and report which checks actually ran.

Optional Git hook linting mirrors CI:

```sh
pip install -r requirements.txt
pre-commit install
pre-commit run --all-files
```

## Documentation and scope

- Keep READMEs and `examples/` consistent with implementation. OpenCode V2 uses
  `plugins` in `opencode.json(c)`; include the published `$schema` in examples.
- Releases are tag-based: repo-wide `v<semver>` tags, `VERSION` as the source of
  truth, `CHANGELOG.md` and the release commit generated by release-it. The
  Create Release Tag workflow derives the version from Conventional Commits and
  must be seeded with an explicit `tag` input for the first release. Do not add
  npm publishing, Docker, or Helm release steps.
- GitHub installation must select the individual package with
  `github:egose/opencode-plugins#<revision>::path:packages/<plugin-name>`, not the
  private repository root. `<revision>` may be a branch, a tag, or a full commit
  SHA; only full SHAs pin the installed revision. Do not claim remote
  installation was verified before the required files are committed and pushed.
- Preserve unrelated user changes. Do not modify global OpenCode configuration,
  install plugins into the user's running setup, or replace existing local
  plugins unless explicitly requested.
- Do not commit, push, publish, or perform destructive Git operations without
  explicit authorization. Keep changes limited to the requested work.
